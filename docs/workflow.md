# 当前固定工作流

## 阶段与职责

| 阶段 | 负责代码 | 行为 |
|---|---|---|
| 邮箱连接与读取 | `imap-connection.js`、`imap-source.js`、`imap-receipts.js`、`db.js` | 统一代理 / TLS 参数，只读 INBOX；全窗口 UID 搜索，过滤已完成 UID 后逐封读取与 MIME 解析 |
| 代码预选 | `triage.js`、`sync-service.js` | 精确日期过滤；忽略营销等非本人进度；按邮件 ID、正文哈希和分析版本去重 |
| 模型确认 | `llm-service.js` | 只在有待分析邮件时发送无邮件内容的 JSON 探测；临时上游故障最多三次，合计仍受探测预算限制 |
| 邮件分析 | `llm-service.js`、`concurrency.js` | 受控并发；仅分析当前邮件；校验结构化输出 |
| 归一与写入 | `normalize.js`、`thread-resolver.js`、`sync-service.js`、`db.js` | 在本地结合公司、岗位和发件人信号归并；按时间顺序逐封落库；保留人工修正 |
| 前端回显 | `sync-stream.js`、`app.js` | NDJSON 进度与心跳；持续刷新已提交记录、日历；支持取消 |

客户端将模型确认和邮件分析分别显示为「Agent连通性确认」和「Agent解析」。历史申请不进入 LLM 提示词。当前没有外部搜索、工具调用、多轮 Agent 或自动公司知识库。

## 时间预算

| 等待步骤 | 默认上限 | 环境变量 |
|---|---:|---|
| 创建客户端 / 连接 | 各 15 秒 | `SYNC_CONNECT_TIMEOUT_MS` |
| 打开收件箱 | 10 秒 | `SYNC_LOCK_TIMEOUT_MS` |
| IMAP 搜索 | 10 秒 | `SYNC_SEARCH_TIMEOUT_MS` |
| 读取下一封 | 20 秒 | `SYNC_FETCH_TIMEOUT_MS` |
| MIME 解析 | 5 秒 | `SYNC_PARSE_TIMEOUT_MS` |
| 退出邮箱 | 2 秒 | `SYNC_LOGOUT_TIMEOUT_MS` |
| 模型连通性确认 | 8 秒 | `SYNC_PREFLIGHT_TIMEOUT_MS` |
| 一次模型请求与响应正文 | 90 秒 | `SYNC_MODEL_TIMEOUT_MS` |
| 一封邮件含重试 / 截断升级 | 90 秒 | `SYNC_MESSAGE_TIMEOUT_MS` |
| 整轮同步 | 180 秒 | `SYNC_RUN_TIMEOUT_MS` |

正整数毫秒，最大 600000；无效配置采用默认值。超时工具同时传递取消信号并限制等待，覆盖响应正文读取。它不能抢占同步 CPU 运算。整轮上限覆盖上述串联阶段。

HTTP 200 响应内的上游错误也按真实错误码处理。普通短暂请求故障最多尝试三次，但共享单封时间预算；截断可在分类器内增加一次输出预算。超时 / 截断耗尽不重复重试该邮件。401、402、403、404、参数错误与 429 停止新派发，已有成功结果保留。

## 续处理与回显

同一邮箱同时只允许一轮同步。取消、限流、模型配置失败、整轮超时后，水位线不能越过最早失败或未完成邮件。同步历史记录停止原因、完成与待续处理数。

前端每 2 秒收到后端心跳，连续 15 秒无流数据则停止等待。已提交记录最多每 500 毫秒刷新一次。同步按钮变为红色取消按钮，请求结束后恢复；邮箱名称与单行蓝色状态在固定高度区域内居中，进度条独立定位于状态下方，显隐不移动邮箱名称。长状态可通过悬停查看完整信息。

IMAP 正文读取仍先于模型阶段：读完本轮待处理邮件后按时间排序；模型结果则逐封处理，无需等待整批结束。若大窗口读取超过整轮预算，应缩小窗口。`maxMessages` 仅选择尚未完成 UID 中最新 N 封；存在未读取邮件时水位线保持保守。`dryRun` 仍读取完整所选范围作预选，不调用模型、写入申请或保存 UID 完成记录。

UID 完成记录按账户、服务商、实际邮箱、文件夹、UIDVALIDITY 和处理版本隔离。分析成功且归档/申请关联有效、或代码明确忽略后才确认完成；失败、取消及未派发邮件不确认。日期搜索的边界安全垫邮件只在仍处于当前窗口之外时跳过，扩大窗口后重新处理。新增 UID 即使日期较早或复用 Message-ID，也不凭日期或邮件 ID 跳过。未知 UIDVALIDITY 时保守读取；分析版本变更、相关归档/申请关联删除会使对应完成记录失效。

旧库没有可靠 UID 映射，升级后需要一次正文读取建立完成记录，继续沿用原有内容去重，不改写历史指纹。完成后再次同步同窗口只搜索 UID，正文读取与模型调用为零（若没有新邮件、失败重试或版本变化）。同步历史区分 `sourceSearched`、`sourceCached`、`sourceFetched`、`sourceDeferred`，避免把搜索总数误认为重新分析数。

设置表单在异步请求前捕获表单引用，保存后清空输入密钥。模型 / 邮箱测试使用已保存配置；模型测试不发送邮件，可能消耗调用额度。页面显示实际启用供应商，保存与连通性是分别可见的状态。

## 进展历史与申请归属

「进展历史」统一展示邮件进展和用户真正新增的无邮件进展，后者标注「手动记录」。改名、合并、拆分只调整申请身份或归属，其技术日志不作为招聘进展展示。仅修改公司或岗位不会新增进展或推进真实进展日期；修正邮件的状态、时间、备注绑定原邮件，随邮件一起移动。编辑无邮件手动记录直接修正原条目，「手动添加进展」才新增条目。

列表根据真实进展的邮件收件时间或手动录入时间筛选、排序，事件日期用于日历。新增进展明确选择独立申请或已有申请；同公司、同岗位仍可表示不同申请。较早邮件重复分析不能撤回后录入的状态，更晚的新邮件仍可推进进展。

合并先选择保留目标并预览完整历史、最终申请字段和邮件数量，再在单个事务中移动所有进展与关联邮件。源申请软归档，正文不改写，合并前的各申请分组保留用于后续选择或恢复。

拆分在统一历史中多选真实进展，只填写新申请的公司、岗位。预览分别显示原申请保留、新申请得到的历史与邮件，双方状态、日期从各自最新真实进展推导；确认后所选进展的全部相关邮件及修正一起移动。原申请至少保留一条进展，新申请可以使用相同公司和岗位。

「恢复合并前申请」预览最近一次完整合并的原分组后恢复原申请。若部分原进展已移出、申请归属已发生不兼容变化，或旧日志缺少完整分组信息，则不能完整恢复，页面显示原因；仍可按当前历史拆分。恢复同样不新增进展。

合并、拆分、恢复都使用数据库事务和预览版本检查，版本过期返回 409 并要求重新预览。每封邮件保存完整的人工确认归属集合，包括共享邮件的其他申请；旧邮件再次分析不能改变该集合。同步提交时重新读取当前申请，避免等待期间的人工调整失效；同名岗位存在明确拆分时，新邮件保守归入原申请并标记待复核，不自动抹除独立申请。

`GET /api/progress/:id/structure` 返回 `thread`、统一 `history`、原申请 `groups`、完整恢复可用性 `restore`。历史项含 `id`、`kind`、当前 `threadId`、时间/状态/备注及 `messageIds`、邮件摘要；预览中的 `threadId` 指向当下实际邮件归属，供页面读取原文。`manual-history` 仅作为兼容接口返回真实无邮件手动记录。

`POST /api/progress/:id/split-preview` 与 `split` 接收 `historyIds`、`company`、`position`、`expectedUpdatedAt`；预览输出 `original` 和 `newApplication` 两侧摘要与历史。`restore-preview` 接收 `mergeEventId`，`restore` 再携带预览版本。合并预览返回完整 `history`，不把技术操作快照混入进展。
